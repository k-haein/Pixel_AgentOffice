# omo·OpenAgent 레퍼런스 연구 + 2층 협업 이식 계획

> 날짜: 2026-07-02
> 형식: 질문 → 답변 → **배운 점 / 결정** (시간 순)
> 맥락: 오픈소스 참고 스택 **omo(`oh-my-openagent`) + 기반 엔진 OpenAgent**를 분석하고,
>       거기서 **멀티모델 + 에이전트 팀 협업**을 PixelAgentOffice로 가져올 수 있는지 검토한 세션.
> 목적: "그때 뭐 알았더라?" 되돌아보기용 — 특히 **내가 몰랐다가 알게 된 것들** 위주로 기록.

## 0. 출발 질문 — "이거 여러 모델 쓰는 채팅방 맞아?"

**나**: omo/OpenAgent가 여러 AI 모델을 한자리에서 쓰는 채팅방인 줄 알았다. 맞아?

**Claude**: 절반만 맞음.
- 맞는 부분: 다수 프로바이더(Claude/Gemini/OpenAI/OpenRouter/Ollama…) 멀티모델 지원.
- 틀린 부분: "채팅방"이 아니라 **AI 코딩 어시스턴트** 스택. 파일 읽기/쓰기·터미널·에이전트 협업을 실제로 수행하는 도구. Claude Code에 가까움.

**💡 배운 점**: "멀티모델 채팅"과 "코딩 에이전트"는 다르다. omo/OpenAgent는 후자.

## 1. 목적 공개 — 이걸 기반으로 내 서비스를 만들고 싶다

**나**: 코딩 지식 없는 일반인도 뭘 할 수 있는지 쉽게 설명해줘. 내 목적은 이 원리를 기반으로 **새 커스텀 서비스**를 만드는 것.

**나 (구체화)**: 두 가지를 생각 중.
1. 내 개인 포트폴리오 개발용 도구
2. 부업 자동화 시스템 에이전트

**Claude**: 둘 다 이 스택의 원리와 맞음. 다만 원본은 개발자용이라 진입장벽 있음.

**💡 배운 점**: 방향에 따라 "재활용할 것"과 "새로 만들 것"이 갈린다.

## 2. 서비스형 구성 — 관리자 vs 사용자 분리

**나**: 이런 스택을 여러 명이 쓰는 서비스로 굴리면 구조가 어떻게 돼?

**Claude**: 보통 **관리자 영역**(계정·API키·사용량·한도 관리)과 **사용 영역**(AI와 작업하는 본체)을 분리한다.
- 나뉜 이유 = **보안 + 역할 분리**. (주방/홀 비유. 관리자 기능 노출되면 AI 무제한 사용·비용 폭주)

**💡 배운 점**: 여러 명이 쓰는 서비스는 "쓰는 곳"과 "관리하는 곳"을 분리하는 게 정석.

**나**: 나는 혼자 쓸 거다. 나중에 서비스할 수도 있지만 우선 혼자.

**결정**: 혼자 쓰는 동안엔 관리자 영역 거의 불필요. 분리는 서비스화 때 의미.

**나**: 이 스택 그대로 쓸 생각 없다. **구조와 기능을 배워서 내 것을 새로 만들** 거다.

1. 멀티모델 연결
2. 로그인/계정 관리

## 4. 🔑 반전 — 내 프로젝트(PixelAgentOffice)가 이미 절반을 갖고 있다

**Claude**: PixelAgentOffice를 분석해보니, 4개 중 **2개는 이미 있음**.

| 기능 | PixelAgentOffice 현재 | 필요 작업 |
|---|---|---|
| 멀티모델 | ✅ 있음 (Claude+Gemini) | 확장만 |
| 로그인/계정 | ❌ 없음 (로컬 BYOK) | 신규 (서비스화 때) |
| 사용량/한도 | ✅ 있음 (dailyLimitUsd) | 서버화(필요시) |
| **에이전트 팀** | ⚠️ 시각 연출만 | **진짜 협업 로직 이식** |

**💡 핵심 통찰**: 지금 PixelAgentOffice의 "팀"은 캐릭터가 자리에 앉은 **시각 연출**일 뿐, 실제로 협업(위임)하진 않는다. omo는 **진짜로** 오케스트레이터가 하위 에이전트에게 위임하고 결과를 모은다. → **#4가 진짜 차이이자 킬러 기능.**

## 5. 1층/2층 구상 + "서버 꼭 필요해?"

**나**: 내 구상 = 1층은 가벼운 대화, 2층은 omo식 에이전트 팀 협업. 더 친근한 UI로 에이전트를 쓰고 싶었던 게 프로젝트의 시작. **서버로 전환해야 하는 이유가 뭐야? 이식 가능해?**

**Claude (코드 확인 후)**: **서버 불필요. 이식 가능.**
- OpenAgent가 서버(:4096)를 둔 이유 = UI와 엔진이 **다른 프로세스**라서. 내 앱은 **Electron main 프로세스가 이미 그 서버 역할** (IPC = HTTP인 셈).
- 서버가 필요한 경우 3가지(다중 로그인 SaaS / 기기 동기화 / 키 숨김) — 혼자 BYOK면 전부 해당 없음.
- 멀티모델 = 쉬움. 협업 = 가능(단 tool-calling 추가 필요).

**💡 배운 점**: "서버"는 UI와 두뇌가 분리됐을 때 필요한 다리. Electron 앱은 이미 그 다리를 IPC로 갖고 있다.

## 6. 미래 — 모바일/태블릿 서비스하면 그땐?

**나**: 나중에 서비스해서 모바일/태블릿으로도 보고 싶다. 그럼 서버 필요해?

**Claude**: **그때는 필요.** Electron은 데스크탑 전용, 폰에선 안 돎. 폰에 API 키 넣어 배포 불가.
- 좋은 소식: 내 코드는 Electron에 묶인 게 **딱 3군데**(`main.ts` 통신, `store.ts`/`usage.ts` 저장 경로). 나머지 "두뇌"(`electron/llm/`)는 순수 Node라 서버로 복붙 이동 가능.
- **2단계 로드맵**: [1단계] 데스크탑 혼자 → [2단계] 두뇌 그대로 + 껍데기(통신·저장·로그인)만 서버로 교체.
- **지금 지킬 원칙**: `electron/llm/`·`electron/agent/`에 `electron`을 import하지 말 것. → 나중 전환 저렴.

**💡 배운 점**: 지금 서버부터 만들 필요 없다. **두뇌를 Electron과 분리해 짜두면** 서비스 전환이 싸진다. OpenAgent가 그 "2단계 서버 버전"의 살아있는 참고 코드.

**결정**: 서버 없이 데스크탑으로 2층 완성 → 두뇌 분리 원칙 준수 → 서비스는 나중에.

## 7. 💰 과금 — 돈이 많이 드나? (병렬 조사)

**나**: 이 스택은 과금을 어떻게 해? 운영하면 돈 많이 드나?

**Claude (에이전트 조사 후)**: **기본적으로 청구 안 함. 운영자 비용도 원칙적으로 0원.**

| 경로 | 누가 냄 | 활성? |
|---|---|---|
| BYOK (자기 키 직접결제) | 사용자 각자 | ✅ 실사용 |
| 크레딧 게이트웨이(Stripe) | 카드 | ❌ 원본 잔재, 죽은 코드 |
| 관리자 키 주입(공유키) | 운영자 | ⚠️ 옵션만 |

- 실사용 = BYOK. 마크업 없음.
- 크레딧/Stripe 경로는 원본 잔재로 미연결(테스트 모드 흔적만). **돈 안 나감.**
- ⚠️ 유일한 돈 새는 시나리오: 서비스화 때 내 OpenRouter 키를 여러 명에게 나눠주면 내 계정 청구 → 사용자별 한도 필수.

**💡 배운 점**: omo/OpenAgent도 PixelAgentOffice도 **BYOK 철학이 같다.** 혼자 쓰는 동안 추가 과금 로직 전혀 불필요.

## 8. 협업 코드 추출 — "복사"가 아니라 "재구축"

**나**: 협업 코드에서 정확히 뭘 발라내야 하는지 매핑해서 개발 세션에 넘길 문서로 정리해줘.

**Claude (에이전트 조사 후)**: **통째 복사 불가.** 협업 심장부(`session/prompt.ts` 71KB)가 OpenAgent 인프라(Storage/Bus/Instance/Compaction)에 강결합. 하지만 **원리는 5개로 압축됨**:
1. 대화 트리(팀장→팀원 자식 대화)
2. 에이전트 루프(LLM→도구실행→반복)
3. 위임 도구(팀장이 팀원 호출)
4. 재위임 방지(팀원엔 위임도구 제외)
5. 진행상황 스트리밍(→ 게임 캐릭터 연출)

→ 이 5개를 PixelAgentOffice의 깨끗한 구조 위에 **수백 줄로 재구축**하는 게 정답.

**만들 것 4개**: ①LLM에 tool-calling 추가(핵심) ②에이전트 루프 ③위임 도구 ④멀티모델(Vercel AI SDK 권장 — tool-calling+멀티모델 동시 해결).

**저장**: `PixelAgentOffice/docs/2F-collaboration-handoff.md` (개발 세션 전달용 핸드오프 문서)

**💡 배운 점**: 오픈소스를 "베낀다"기보다 **"원리를 배워 내 구조에 맞게 다시 짠다"**가 더 빠르고 유지보수 쉽다.

## 9. 🧠 용어 정리 — OpenRouter vs OpenAI vs Vercel AI SDK

**나**: OpenRouter랑 OpenAI 어쩌구가 뭐야? 여러 모델 한자리에서 쓰고 연결도 한번에 하는 거 같은데. **agent도 OpenRouter가 자동으로 만들어줘?**

**Claude**:
| 이름 | 정체 | 비유 |
|---|---|---|
| OpenAI | AI 만드는 **회사** (GPT) | 식당 |
| OpenRouter | 여러 모델을 키 하나로 쓰는 **중개 서비스** | 배달앱 |
| Vercel AI SDK | 내 코드에 넣는 **부품** (통일된 호출) | 주문서 |

- **OpenAI ≠ OpenRouter** (전혀 다른 회사).
- **agent는 OpenRouter가 안 만든다.** OpenRouter는 "이 질문 이 모델에 전달"만. 협업/에이전트 로직은 **내 코드**가 만든다.

**💡 배운 점 (중요)**: 연결(OpenRouter/AI SDK)과 에이전트(내 코드)는 완전히 다른 층. "여러 모델 한자리"는 서비스가 해주지만 "AI들이 팀으로 협업"은 내가 짜야 한다.

## 10. agent 역할은 수동 노가다인가? + 출처 구조(omo/OpenAgent)

**나**: 그럼 역할 있는 agent는 **수동 노가다로 기획**한 거야? 그냥 개발팀 방식 따라간 거야?

**Claude**:
- **네, 인격/역할은 사람이 쓴 긴 시스템 프롬프트다** (오케스트레이터 프롬프트 50.6KB = 소설 몇 챕터 분량). 연결 계층(OpenRouter 등)은 "어떤 모델 쓸지"만 담당.
- 스택은 두 층: **OpenAgent**(엔진 뼈대 — 세션/도구/루프) + **`oh-my-openagent`(omo)**(에이전트 인격 팩, 제작자 code-yeongyu).

**나**: omo 원본을 1차 참고로 문서에 추가해줘. 역할을 왜 저렇게 나눴을까?

**Claude**: 역할 분담은 **인간 팀을 닮았지만, 진짜 이유는 AI 기술적 한계**다:
1. 컨텍스트 오염 방지 (한 AI가 다 하면 머리가 잡동사니로 참)
2. 병렬 처리 (여러 팀원 동시 실행)
3. **비용 최적화** (단순=싼 모델, 어려움=비싼 모델)
4. 검토 독립성 (만든 자는 자기 실수 못 봄)
5. 기획/실행 분리 (섞으면 둘 다 질 저하)
- 그리스 신화 이름도 의미 있음: Sisyphus(안 멈춤)=팀장, Momus(비난의 신)=검토자, Hephaestus(대장장이)=일꾼.

**💡 배운 점 (핵심)**: **역할 분담은 "예쁜 게임 설정"이 아니라 "AI가 잘 작동하기 위한 기술적 필수"다.** 2층 협업을 제대로 하려면 팀장/팀원 분리가 연출이 아니라 조건.

**저장**: 핸드오프 문서에 omo 원본을 1차 참고로 등재.

## 11. 직급 ↔ 모델 배정 (omo agent-model-matching 착안)

**나**: omo의 agent-model-matching을 내 직급 시스템에 녹여줘.

**Claude (agent-model-matching 전문 확인 후)**: omo의 진짜 철학은 "비싼 모델=좋음"이 **아니었다.** **"모델 = 성격 다른 개발자"** — 계열마다 잘하는 일이 다르다:
- Claude/Kimi/GLM = 소통형(지시 잘 따름, 글쓰기)
- GPT = 자율형(목표만 주면 알아서 깊게)
- Gemini = 시각형(UI/UX·디자인)

→ 그래서 모델 배정은 **두 축**: ①직급(난이도/비용) ②직무·성격(계열).
→ PixelAgentOffice엔 이미 `TEMPLATES`(편집자/작가/개발자) + `MBTI`가 있어 **2차원 매칭** 가능.
→ 세션 11의 "Leader=Opus, 기록=Sonnet"은 축①의 씨앗이었고, 여기에 축②(계열)가 더해짐.
→ 게임 재미: **진급=직원이 똑똑해짐**(성장 실감) + 비용 자동 통제.

**명언(omo 원문)**: *"단순 탐색에 Opus 쓰지 마라 — 시니어한테 서류정리 시키는 격."*

**저장**: `ideas/11-rank-system.md` §9.5 상세 정리 (2축 매칭 표 + omo 카테고리 + fallback 개념).

**💡 배운 점 (2개)**:
1. 비용 통제와 게임 재미를 **직급 하나로** 잡을 수 있다.
2. 모델 선택은 "급"만이 아니라 **"성격/계열"** 축도 있다 — 내 캐릭터 직무(TEMPLATE)와 딱 연결됨.

## 12. 🔧 실제 구현 방식·단계 정리

**나**: 이제 실제 구현은 어떤 방식으로, 어떤 흐름·단계로 하면 돼?

**Claude**: 기존 M1~M3 방식 그대로 — **한 세션=한 단계, 눈으로 확인, 되면 커밋**. 시작 전 딱 하나 잠글 결정 = **Vercel AI SDK 도입 여부(강력 추천)**. 단계는 의존성 순서(건너뛰기 불가):

| 단계 | 결과물 | 눈으로 볼 것 |
|---|---|---|
| M-2F-0 | 멀티모델 | 새 모델로 대화됨 |
| M-2F-1 | tool-calling | AI가 도구 왕복 |
| M-2F-2 | 에이전트 루프 | 도구 여러 번 이어 씀 |
| **M-2F-3** | **위임 협업** | **팀장→팀원 실제 협업** |
| M-2F-4 | 게임 연출 | 캐릭터가 협업 반응 |

**💡 배운 점**: "전화번호부(멀티모델) → 도구 주고받기(calling) → 반복(루프) → 팀원 넘기기(위임)" 순서로 쌓인다.

## 13. 🧠 AI 기초 개념 학습 (내가 몰랐던 것들)

**나**: AI SDK·멀티모델·에이전트 루프·calling… 기초 지식이 없다. 아주 쉽게 비유로 설명해줘.

**Claude**: "전화 비유"로 통일 설명 —
- 모델=전문가, API=직통전화, 멀티모델=전화번호부, AI SDK=만능 전화기
