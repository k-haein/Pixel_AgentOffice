## 📌 30초 요약

AI 에이전트는 강력하지만 **일반 사용자에겐 진입 장벽이 너무 높다**. 코드, 터미널, JSON 설정, 추상적 오케스트레이션 개념. 그런데도 많은 일반 사용자가 ChatGPT/Claude 앱에서 **"인격을 부여한 페르소나 채팅"**(편집자, 칸트, 작가 등)을 일상적으로 사용한다.

**PixelAgentOffice는 이 행동을 "픽셀 사무실 + 직원 관리 게임"으로 게임화**한다:
- 🐙 픽셀 캐릭터를 "직원"으로 채용 (Mary 편집자 / Haewol 작가 / Cody 개발자 / 커스텀 문어)
- 🎯 이름·역할·성격(MBTI 16종)·외형·모델을 시각적으로 설정
- 💬 더블클릭/말풍선으로 대화 — 응답에 따라 머리 위 **감정 이모지**(12종)가 실시간 변화
- 📝 책상 위 메모지로 직원 관리 + 기본 감정 설정 + **메모리(기억) 요약**
- 📈 대화·메모 활동이 쌓이면 **직급 진급 요청** (활동/시간/정성형 등 진급 방식 선택)
- 🛒 상점에서 가구 구매 → 드래그/배치로 내 사무실 꾸미기
- 🌙 일일 비용 한도 도달 시 **강제 야간** (시그니처 폴리시 — 이제 실제 차단)
- 🎓 첫 실행 시 **문 비서**가 사장님(사용자)에게 회사를 안내하는 튜토리얼

**차별점(현재)**: 단순 채팅 도구가 아닌 *"애착이 생기는 환경"*. 다만 이 차별점이 **진짜 해자(moat)인지는 미검증** — §2.4·§8에 정직하게 기록. 강한 차별화 전략은 출시 후 v3에서 정립 예정.

**현재**: v0.0.1 portable `.exe`를 외부 테스터에게 배포 → 1차 피드백("튜토리얼/온보딩 필요", 버그 2건)을 반영해 **v0.0.2로 빌드 완료**한 단계 (커밋·푸시·Releases 업로드 대기).

## 1. Problem · 풀고자 한 문제

### 1.1 외부 문제 (사용자 관찰)

- **AI 에이전트 도구의 진입 장벽**: 대부분의 멀티 에이전트 도구(AutoGen, CrewAI 등)가 개발자 대상. 일반 사용자는 코드 작성·YAML 설정·터미널 실행을 못 함.
- **하지만 일반 사용자도 "페르소나 대화"는 이미 잘 쓴다**: ChatGPT/Claude 앱에서 "당신은 편집자입니다", "당신은 철학자 칸트입니다" 같은 시스템 프롬프트 활용.
- **격차**: 페르소나 대화 사용자 ↔ 멀티 에이전트 도구 → 중간 다리가 없음.

### 1.2 관찰 사례
> 본 프로젝트 사용자의 동생: 글 작업할 때마다 ChatGPT 채팅창에 "당신은 편집자입니다. 원고를 받으면..." 를 반복 입력. **같은 페르소나를 재사용하고 싶지만 채팅창 분리가 안 됨.**

### 1.3 기존 솔루션 한계

| 기존 도구 | 한계 |
|---|---|
| Claude.ai Projects | 페르소나 분리는 OK, 다만 멀티 에이전트 X, 시각적 매력 X |
| AutoGen / CrewAI | 개발자 전용, 시각화 X |
| ChatGPT Custom GPTs | 분리 OK, 무료 사용자 제한 |
| Character.ai | 캐릭터 매력 ↑, 작업 도구로는 약함 |

→ **"애착 가질 수 있는 작업 도구"의 빈자리.** (단, 이 빈자리가 충분히 큰지·방어 가능한지는 §2.4 참조)

## 2. Vision · 차별화

### 2.1 한 줄 비전

> "*Two Point Hospital + The Sims + AI Town*의 게임 메커니즘으로 AI 에이전트 관리를 풀어낸다."

### 2.2 핵심 차별점 3가지

| | 기존 도구 | PixelAgentOffice |
|---|---|---|
| **설정** | 코드/YAML 작성 | 캐릭터 선택 + 이름 짓기 + MBTI 부여 |
| **관리** | JSON 그래프 / 명령어 | 책상 위 📝 메모지 클릭 + 진급 |
| **모니터링** | 로그 응시 | 사무실 둘러보기 + 직원 감정 이모지 |
| **에러** | 빨간 메시지 | 직원이 시무룩해함 / 친절 한글 안내 |

### 2.3 디자인 원칙

1. **사용성 + 재미를 동시에** — 기능만 동작하는 도구가 아닌, *내 사무실에 애착이 생기는* 환경.
2. **사용자 부담 최소화** — 사용자는 "지침"만 직접 관리, "메모리"는 시스템이 백그라운드 처리.
3. **점진적 노출** — 첫 실행 시 **문 비서 튜토리얼**(강제 메리 채용 → 채팅 → 메모/상점/설정 안내). 익숙해지면 MBTI·진급·꾸미기 등 게임적 요소 자연스럽게 확장.
4. **픽셀 일관성** — 모든 요소(캐릭터·책상·가구·UI)를 같은 픽셀 그리드 시스템으로 통일. (단, 12×12 그리드의 시각 한계 → 고해상도 디테일은 PNG asset 도입 시 확장 예정)

### 2.4 차별점에 대한 정직한 평가 ★ (v0.0.2 신규)

> 포트폴리오 정직성을 위해, "강한 차별점이 있는 척"하지 않고 **현재 상태를 솔직하게** 적는다.

- **현재 차별점 = "시각적 매력 + 캐릭터 애착 + 게임적 재미"** 다. 이것은 *경험의 차별점*이지, 기능적으로 **대체 불가능한 해자(moat)는 아니다.**
- 핵심 기능(페르소나 분리·지침 재사용·여러 에이전트 관리)은 사실상 **Claude Projects / Custom GPTs로도 상당 부분 대체 가능**하다. 우리는 "더 쉽고 더 정겹게"일 뿐, "여기서만 되는 것"은 아직 약하다.
- 즉 **"왜 이걸 써야 하는가"에 대한 방어선이 아직 얇다.** 재미·애착이 리텐션으로 이어지는지는 v0.0.1 테스터 피드백으로 검증 중.
- **결정**: 강한 차별화(해자) 전략 — 예: 멀티 에이전트 협업 워크플로우(Phase 2 Seegene 임포트), 로컬 파일/작업 연동, 캐릭터 성장 서사 — 은 **출시 후 v3에서 본격 정립**한다. v0.0.2 PRD는 그 전략을 *아직 적용하지 않은 현재 상태*로 기록한다.
- 상세 보류 근거: `HANDOFF §6.P (페르소나/해자 → v3)`, `ideas/00-brainstorming-log §130`.

## 3. Target Users · 페르소나

### 3.1 Primary — *"페르소나 채팅을 일상적으로 쓰는 일반 사용자"*

| 항목 | 내용 |
|---|---|
| 직군 | 작가, 학생, 디자이너, 마케터, 1인 사업자 |
| LLM 사용 경험 | ChatGPT/Claude 무료 또는 Pro 구독 사용 중 |
| 페인포인트 | 페르소나마다 채팅창 분리 안 됨, 매번 시스템 프롬프트 복붙, 캐릭터 일관성 부족 |
| 기대 | "내 글쓰기 도우미 Mary"가 매번 같은 톤으로 답해주길 |
| 기술 수준 | 코드 못 씀, GUI만 가능 |

### 3.2 Secondary — *"AI 도구 얼리어답터 / 개발자"*

| 항목 | 내용 |
|---|---|
| 직군 | 개발자, AI 엔지니어, 프로덕트 매니저 |
| LLM 사용 경험 | API 키 사용 익숙, 여러 모델 비교 |
| 페인포인트 | 자기 워크플로우에 맞는 에이전트 도구 부족, 멀티 에이전트 시각화 도구 부족 |
| 기대 | 자기 프로젝트 에이전트들을 시각화하고 싶음 (Phase 2: Seegene 같은 케이스) |
| 기술 수준 | 코드 작성 가능 |

### 3.3 Anti-Persona — 본 도구가 적합하지 않은 사람

- 단순히 한 번 쓰고 마는 사용자 (커스터마이징 가치 0)
- 진지한 협업 워크플로우 필요 (B2B SaaS 영역)

## 7. Technical Architecture

```
┌──────────────────────────────────────────────────┐
│         PixelAgentOffice-0.0.2-portable.exe        │
│                                                    │
│  ┌─ Renderer (Chromium) ─────────────────────┐     │
│  │  React 19 + Phaser 4                       │     │
│  │  ├─ Phaser canvas (사무실 씬)              │     │
│  │  ├─ React DOM (모달/채팅/상단바/튜토리얼)   │     │
│  │  └─ src/platform/ (Platform Adapter)       │     │
│  └────────────┬───────────────────────────────┘     │
│               │ IPC (preload.ts) / platform.* 추상화 │
│  ┌────────────▼─────────────────────────────────┐   │
│  │  Main Process (Node.js)                      │   │
│  │  ├─ data/store.ts (JSON 영속화)              │   │
│  │  └─ llm/ dispatch·anthropic·gemini·usage·    │   │
│  │     errorMessages·apiKeys(safeStorage)       │   │
│  └──────────┬───────────────────────────────────┘   │
└─────────────┼─────────────────────────────────────┘
              │ HTTPS
       ┌──────▼──────────┐
       │  Anthropic /    │
       │  Google         │
       └─────────────────┘
```

**핵심 디자인 결정**:
- **Hybrid 렌더링**: Phaser(게임 씬) + React(UI 모달). 각자 강점.
- **Platform Adapter**: `src/platform/`로 Electron API 격리 → 미래 Web/모바일 진입 시 컴포넌트 코드 무변경.
- **Provider Abstraction**: `LLMProvider` 인터페이스로 Groq/Ollama 추가 용이. dispatch → registry → anthropic/gemini, 타입화된 `LLMError` 분류(DAILY_LIMIT 포함).
- **일일 비용 영속화**: 날짜별 키(`usage-daily.json`) + 원자적 쓰기(temp+rename) + main 프로세스 하드 차단.
- **API 키 분리 저장**: provider별 별도, OS 키체인 암호화.
- **픽셀 렌더링**: `drawPixelGrid()` 문자열 배열 → 픽셀 사각형. 12×12 한계는 PNG asset로 확장 예정.

### 7.1 테스트 피라미드 (Day 14 복구)

| 층 | 도구 | 특징 |
|---|---|---|
| 유닛 | **vitest** | 순수 함수(promotion/seats) 24개. 앱·브라우저 불필요, ~1초. 빠른 회귀 그물 |
| 통합 | (RTL, 후속) | 컴포넌트 단위 |
| E2E | **Playwright** | 실제 Electron 실행. 빈 사무실 채용·API 키 흐름 9개 (격리 임시 userData에 시드) |

> **적대적 리뷰 ≠ 실행 테스트**: AI가 코드를 읽어 결함을 찾는 적대적 리뷰는 *정적 분석*이고, 앱을 띄워 동작을 확인하는 건 E2E/유닛이다. 둘은 보완 관계.

### 7.2 알려진 기술 부채 (v3 정리 예정)

- 일부 god-file(App.tsx·OfficeScene.ts 등) 비대 → 모듈 분해 필요
- `eventBus`가 stringly-typed → 타입 안전성 약함 (이벤트 이름 오타 컴파일타임 미검출)
- 튜토리얼 로직이 App에 산재 → `useTutorial` 훅 추출 후보
- → **출시 후 v3에서 리팩토링**. `HANDOFF §6.Q` 참조.

### 7.3 Electron이란? (비개발자용)

> **Electron** = 웹 기술(React/HTML/CSS)로 데스크탑 앱(.exe)을 만드는 프레임워크. VS Code, Discord, Slack, Notion이 모두 Electron 기반. `.exe` 더블클릭 즉시 실행 + 웹 기술 재사용 + OS 키체인/파일 접근. 한계는 iOS/Android 미지원(데스크탑 전용) → 모바일은 Platform Adapter로 격리해 후속 대응.

## 8. Business Model

### 8.1 검증된 한계
> "이미 Claude를 쓰는 사람에게 UI만 무료 제공" → **Anthropic ToS상 불가능**.

### 8.2 BYOK (Bring Your Own Key) 모델 채택
- 사용자가 직접 API 키 발급 + 결제 / 우리는 비용·법적 책임 0
- 단점: 카드 등록 부담 → 백엔드 프록시(Phase 3)로 완화 검토
- 완화 1차: **데모 모드**(키 없이 둘러보기) + **일일 비용 상한 실제 차단**(과금 사고 방지)

### 8.3 사업성에 대한 정직한 평가 (§2.4 연계)

- 현재는 **수익 모델보다 "사용자가 계속 쓰는가(리텐션)"를 먼저 검증**하는 단계다.
- BYOK는 진입 장벽이고, 차별점(§2.4)이 약하면 "굳이 이걸?"이 된다 → 따라서 **해자 전략(v3)이 사업성의 전제**다.
- v0.0.1 테스터 피드백 → v0.0.2 온보딩 강화 → 리텐션 신호 확인 후 Phase 3(백엔드)·해자(v3) 판단.

본 PRD는 "완성된 것처럼 보이기"보다 **현재 상태를 정확히** 기록한다:
- ✅ 완성·검증 / 🟡 부분·의도적 보류 / 📋 계획 을 명확히 구분
